# 生产级 AI 防御与自动阻断系统升级路线图

> 目标：将当前「演示/学习级」的 AI 防御系统升级为可部署在生产环境的智能安全防线。

---

## 一、现状诊断

### 1.1 已具备的能力
| 模块 | 现状 | 生产可用度 |
|---|---|---|
| 自动隔离系统 | 四级隔离 + 多维度检测 + IP 计数 | 60% |
| AI 决策引擎 | 规则 + 统计 + 时序 + LLM + 威胁情报 | 55% |
| 自适应学习 | 基线学习、规则进化、反馈闭环 | 40% |
| 主动防御 | 动态蜜罐、响应欺骗、攻击者画像 | 50% |
| 权限校验 | JWT 签名 role + 后端二次验证 | 75% |
| 敏感路径拦截 | Vite + Express 双层拦截 | 70% |

### 1.2 关键短板
1. **状态易失**：所有攻击者画像、隔离状态、威胁分数存在内存 Map，后端重启全丢。
2. **无持久化存储**：无 Redis/数据库支撑，无法做集群部署。
3. **限流不统一**：仅 captcha 有严格限流，大部分接口裸露。
4. **缺少 WAF 前置**：所有请求直接打到 Node.js，没有第一道过滤。
5. **情报源单一**：只有本地 reputation，无外部威胁情报 feed。
6. **HTTPS 缺失**：本地 HTTP 开发，生产无法部署。
7. **TS 错误未清零**：`npx tsc --noEmit` 仍有报错，类型安全不足。
8. **密钥管理松散**：API key 存在泄露风险。
9. **无集中日志**：安全事件分散在文件/控制台，无法审计与告警。
10. **缺少回滚机制**：策略升级错误可能导致误封正常用户。

## 三、技术选型

### 3.1 WAF / 反向代理
- **Cloudflare（推荐）**：免费版即有 DDoS 防护、Bot Fight Mode、IP 声誉。
- **Caddy**：自动 HTTPS，配置简单，适合自托管。
- **Coraza WAF**：Go 语言实现的 ModSecurity 继任者，支持 OWASP CRS 规则集，可嵌入 Caddy/Nginx。[参考](http://m.toutiao.com/group/7544267962912342564/)

### 3.2 状态持久化
- **Redis**：攻击者画像、隔离状态、限流计数、会话缓存。
- **SQLite / D1**：审计日志、决策历史、规则库、基线数据。

### 3.3 限流
- **Redis + Sliding Window**：比固定窗口更平滑，适合生产环境。[参考](https://blog.csdn.net/csdn_tom_168/article/details/150478819)
- 也可使用 `express-rate-limit` + Redis Store。

### 3.4 威胁情报
- **AbuseIPDB**：免费 IP 信誉查询。[参考](https://blog.csdn.net/as_asdf/article/details/150450606)
- **FireHOL IP Lists**：开源黑名单集合。
- **IPinfo / ip-api.com**：IP 地理与 ASN 信息。

### 3.5 日志与监控
- **自建**：Winston / Pino + Loki + Grafana
- **SaaS**：Sentry（错误）、DataDog / New Relic（APM）
- 最低要求：结构化日志 + 集中存储 + 告警规则

### 3.6 密钥管理
- 生产环境使用 KMS / 密钥托管服务
- 本地开发使用 `.env`，严禁提交
- 支持 API key 轮转与备用 key

## 五、关键设计决策

### 5.1 为什么用 Redis 而不是纯内存？
- 支持后端多实例部署
- 支持 TTL 自动过期
- 支持原子操作，适合限流和计数
- 重启不丢状态

### 5.2 为什么还需要 WAF 前置？
- AI 防御运行在应用层，消耗 CPU/LLM API 成本
- WAF 先过滤掉 90% 已知攻击和扫描，降低后端压力
- 形成纵深防御，一层失效还有下一层

### 5.3 为什么 Threat Intelligence 用异步？
- 外部 API 查询可能慢或失败
- 首次访问先做本地缓存/默认放行，异步查询后更新画像
- 避免每个请求都阻塞等待外部 API

### 5.4 自动隔离如何避免误伤正常用户？
- 本地 IP / 已知管理员 IP 白名单
- 隔离前必须有「观察期」和「多维度确认」
- 提供手动解封接口 + 自动恢复机制
- 根据业务影响分级：quarantine 只限非核心接口，lockdown 才全阻断

## 六、成本与收益评估

### 6.1 成本
| 项目 | 估算（月） | 说明 |
|---|---|---|
| Redis | 0-50 USD | 自建免费，云服务按需 |
| Cloudflare Pro | 0-20 USD | 免费版够用，Pro 更强 |
| AbuseIPDB | 0 USD | 免费额度足够小型应用 |
| LLM API | 10-100 USD | 取决于流量和模型 |
| 日志平台 | 0-30 USD | 自建 Loki 免费，SaaS 按需 |
| 人力 | 主要成本 | 2-4 周全职开发 |

### 6.2 收益
- 阻断 90%+ 自动化扫描和 bot 攻击
- 将人工安全响应时间从天级降到分钟级
- 降低数据泄露风险
- 满足基础合规要求（审计日志、访问控制）

## 七、风险与回滚策略

| 风险 | 缓解措施 |
|---|---|
| 新策略误封正常用户 | 灰度发布 + 观察模式 + 一键降级 |
| Redis 故障导致系统不可用 | 本地内存降级 + 熔断 |
| LLM API 延迟/故障 | 异步分析 + 超时 fallback |
| WAF 规则误拦截 | 规则观察期 + 白名单 |
| 数据泄露 | HTTPS + 最小权限 + 密钥轮转 |

---

## 八、建议的下一步

**立即开始 Phase 1**，因为：
1. 不修复 TS 错误和基础漏洞，后续所有高级功能都不稳
2. HTTPS、限流、CORS 是生产部署的最低门槛
3. Phase 1 改动相对独立，风险可控

Phase 1 完成后，再做 Phase 2（Redis 持久化），此时系统已经可以初步生产运行。Phase 3-4 逐步增强检测能力。
